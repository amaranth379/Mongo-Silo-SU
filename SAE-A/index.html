Executive Summary

1분 요약: 세 가지 원칙과 첫 번째 미션

① 숫자는 시스템이, 해석은 AI가

AI(LLM)에게 계산까지 맡기면 수치 오류와 누락이 반복됩니다. 합계·전년 대비·순위는 데이터베이스가 미리 계산하고, AI는 검증된 숫자를 설명하고 요약하는 역할만 맡깁니다.

② 회사의 "지도"를 먼저 만든다

법인 → 공장 → 라인 → 설비, 견적 → 오더 → 생산, 기안 → 구매 → 자산처럼 업무 대상 간 관계를 정의한 온톨로지가 있어야 AI가 엉뚱한 데이터를 연결하지 않고 원인을 찾아 내려갑니다.

③ 빠른 답은 "미리 준비된 데이터"에서

경영진이 자주 묻는 지표는 기간·법인·품목별로 사전 집계해 두고, 드문 대규모 분석만 별도로 비동기 처리합니다. 응답 속도와 비용이 동시에 안정됩니다.

세아가 지금 진행 중인 GPT 기반 엑셀·PDF 파싱 → 적재 → AI 프론트 목업은 좋은 출발점입니다. 이 가이드는 그 결과물을 버리지 않고, 운영 가능한 의사결정 플랫폼으로 키우기 위한 구조와 순서를 제안합니다.

01 · 현재 진단

지금의 PoV는 "보이는 결과"를 빠르게 만들었습니다. 다음은 "믿을 수 있는 답"입니다

현재 세아의 방식은 샘플 엑셀·PDF를 GPT API로 파싱해 적재하고, AI로 만든 프론트 화면에서 조회하는 구조입니다. 빠르게 가치를 보여주기에는 적합하지만, 전사 확대 시 아래 문제가 반복해서 나타납니다.

잘하고 있는 점

  • 실제 현업 데이터(자산원장, 매각 이력)로 시작 → 체감 가치가 분명함
  • 엑셀·PDF처럼 형식이 제각각인 자료를 AI로 구조화하는 경험 확보
  • 경영진이 화면으로 결과를 확인할 수 있는 목업 확보

확대 시 나타나는 문제 (샘플 기준 참고)

  • 같은 자산, 다른 이름: 자산코드 중복 332건, 자산명칭이 현지어·약어로 혼재
  • 분류 공백: 미싱·자동화 사전으로 분류되지 않는 자산이 51%
  • 단위·통화 혼재: 달러 서식 숫자와 루피아(RP) 문자열이 같은 열에 공존
  • 조직 기준 불일치: 법인·공장·부서 표기가 파일마다 달라 "법인별 집계"가 사람마다 다르게 나옴

AI가 엑셀을 바로 읽고 답하게 하면 생기는 일

증상예시 (세아 맥락)해결 방향
숫자가 실행할 때마다 다름"인도네시아 2024년 매각 건수"를 물을 때마다 합계·반올림이 달라짐집계는 DB가 계산하고 AI는 인용만
중요 항목 누락유휴 설비가 가장 많은 공장을 빼고 요약규모·변화량 기준 후보를 코드가 먼저 선정
근거 없는 원인 단정"자동화 투자로 유휴 미싱이 늘었다"처럼 확인되지 않은 인과 서술근거 등급(확정 / 주의 / 관찰)으로 구분
같은 질문, 다른 화면목업 화면마다 집계 기준(보유 상태, 조직 범위)이 다름지표 정의를 한 곳에서 고정·버전 관리
02 · 설계 원칙

AI 리포트 자동화의 출발점은 분석 전용 데이터 사일로와 데이터 흐름입니다

대규모 데이터를 운영하며 AI 분석 리포트를 자동화한 선행 사례들은 비슷한 실패를 먼저 겪었습니다. 원천 데이터를 프롬프트에 몰아넣고 한 번에 리포트를 만들게 하자 수치 오류, 중요 항목 누락, 형식 불안정, 얕은 해석이 반복된 것입니다. 해결의 열쇠는 프롬프트가 아니라 원천 시스템과 분리된 분석 전용 데이터 사일로를 두고, 데이터가 흐르는 길을 먼저 설계하는 것이었습니다.

원칙 0 · 데이터 사일로와 흐름을 먼저 구성한다
AI가 ERP · 엑셀 · PDF를 직접 읽게 하지 않습니다. 검증된 데이터만 모이는 분석 전용 사일로를 별도로 만들고, "수집 → 검증 → 사일로 → AI 분석 → 보고 → 결과 재적재"의 흐름을 고정해야 아래 네 가지 원칙이 작동합니다.

운영 시스템 보호

분석 질의가 ERP · MES 같은 운영 시스템에 부하를 주지 않습니다. 공장 운영과 AI 분석이 서로 영향을 주지 않습니다.

하나의 기준

조직 · 분류 · 지표 정의가 사일로 한 곳에서 관리되어, 어느 화면 · 어느 AI 답변이든 같은 숫자가 나옵니다.

축적과 재사용

분석 결과와 근거가 다시 사일로에 쌓여, 다음 질문은 더 빠르고 과거 판단은 감사할 수 있습니다.

사일로 위에서 작동하는 네 가지 원칙

원칙 1계산과 해석을 분리

전일·전월·전년 대비 변화와 상위 변동 항목은 코드가 먼저 계산·선정합니다. LLM은 확정된 수치를 비즈니스 문장으로 만듭니다.

세아 적용: 법인별 보유·유휴 대수, 매각 건수 추이, 자동화 도입률은 MongoDB가 계산합니다.

원칙 2자율성은 "탐색 그래프" 안에서

에이전트가 다음 조사 대상을 스스로 고르되, 이동 가능한 분석 경로(전체 → 상위 분류 → 세부 항목)는 시스템이 제한합니다.

세아 적용: 그룹 → 국가 → 법인 → 공장 → 라인 → 설비 경로를 온톨로지로 정의합니다.

원칙 3섹션별로 필요한 맥락만

요약에는 검증된 원인만, 추세에는 통계만, 기회·위험에는 관찰 신호까지 전달해 과잉 해석을 줄입니다.

세아 적용: 경영 브리핑, 공장별 상세, 리스크 섹션의 입력을 분리합니다.

원칙 4품질을 측정해야 개선된다

모든 실행 과정을 기록(trace)하고, 사람이 정한 평가 기준표(rubric)로 변경 전후를 비교합니다.

세아 적용: 질문·조회·답변·근거를 모두 저장해 재현과 감사가 가능하게 합니다.

다섯 가지 분석 도구 → 세아 적용

분석 도구역할세아에서의 의미 (예시 질문)
drill_down변화를 하위 단위로 분해, 주요 기여자 반환"유휴 설비 증가분은 어느 법인·공장·설비 분류에서 나왔나?"
compare_pattern과거 추세로 신규·성장·감소·일시적·구조적 변화 분류"이번 분기 매각 증가는 일시적인가, 공장 재편에 따른 구조적 변화인가?"
entity_context대상의 메타데이터·변경 이력 조회"이 설비는 언제, 어떤 기안으로 취득했고 어디서 이관됐나?"

참고: AI 리포트 자동화 선행 사례의 설계 원칙, 세아 적용 가안(data_architecture.md).

03 · 전체 구조

세아 AX 데이터 플랫폼: 다섯 단계로 흐르는 하나의 구조

왼쪽의 원천 데이터가 정제를 거쳐 분석 전용 데이터 사일로(MongoDB Atlas)에 모이고, AI는 허브에 준비된 수치와 맥락을 꺼내 쓰며, 결과는 다시 허브에 저장되어 다음 분석에 재사용됩니다.

그림 1. 세아 AX 데이터 플랫폼 전체 구조(가안). ③의 다섯 층은 MongoDB Atlas 안에서 컬렉션 그룹으로 구분되며, 한 시스템에서 운영됩니다.

각 층이 경영진에게 주는 가치

층무엇을 담나경영 관점의 효과
ⓐ 원본 보관층원본 파일, 행·셀 단위 원문, AI 파싱 결과"이 숫자는 어디서 왔나?"에 클릭 한 번으로 원본 엑셀 행까지 제시 → 신뢰 확보
ⓑ 온톨로지층법인·공장·설비·자재·오더·문서와 그 관계조직·용어 기준이 하나로 통일되어 보고서마다 숫자가 다른 문제가 사라짐
ⓒ KPI층기간·조직·품목별 사전 집계 지표자주 묻는 질문은 즉시 답변, AI 비용과 오류를 동시에 줄임
ⓓ 맥락·지식층변경 이력, 기안·주간보고 문서, 정책숫자의 "이유"를 문서 근거와 함께 설명
ⓔ 분석 결과층분석 케이스, 원인 경로, 리포트, 평가 결과과거 판단을 재사용하고, 의사결정의 근거를 감사할 수 있음
04 · 대용량 데이터 전략

응답을 빠르게: "모든 질문을 매번 계산하지 않는다"

글로벌 공장의 데이터가 쌓이면 원본을 그때그때 읽어서 답하는 방식은 느리고 비쌉니다. 운영 중인 AI 리포트 시스템들도 상위 KPI를 매번 다시 조회하지 않고 사전 집계 데이터에서 출발해, 부족할 때만 추가 조회합니다. 세아도 질문을 세 가지 속도 등급으로 나눠 처리합니다.

그림 2. 질문 유형별 응답 경로. 응답 시간은 설계 목표이며 실제 데이터 규모와 클러스터 사양으로 검증이 필요합니다.

대용량에서도 빠르게 유지하는 6가지 원칙

1. 미리 집계해 둔다

적재가 끝나면 기간·조직·품목별 지표를 계산해 KPI 컬렉션에 저장합니다. 이동평균·순위·누적값도 데이터베이스가 계산합니다.

2. 적재 완료 후 분석한다

파일 일부만 들어온 상태에서 리포트를 만들지 않도록 데이터 버전을 확정한 뒤 집계·분석을 시작합니다.

3. 수정 가능한 구조로 둔다

원장은 소급 정정이 잦습니다. 과거 값을 다시 계산하고 덮어쓸 수 있는 일반 컬렉션 구조로 KPI를 관리합니다.

4. 자주 묻는 길에 인덱스

"법인 + 기간 + 분류"처럼 질문 패턴이 정해지면 그 순서대로 인덱스를 만들어 대용량에서도 일정한 속도를 유지합니다.

5. 데이터 온도를 나눈다

최근 데이터는 고성능 저장소에, 오래된 원본과 이력은 저비용 보관소로 자동 이동해 비용을 관리합니다.

6. 큰 탐색은 따로 돌린다

준비된 집계로 답할 수 없는 대규모 분석은 비동기로 처리하고, 결과를 다시 허브에 저장해 재사용합니다.

AI 비용 관점: LLM에 원본 엑셀 전체를 넣는 대신, 이미 계산된 몇 줄의 사실만 전달하면 토큰 사용량과 응답 시간이 함께 줄고 답변의 일관성은 높아집니다.
05 · 온톨로지

회사의 지도: AI가 따라갈 수 있는 업무 대상과 관계

온톨로지는 "우리 회사에는 어떤 대상이 있고, 서로 어떻게 연결되는가"를 정의한 지도입니다. 이 지도가 있으면 AI는 정해진 길(관계)을 따라 원인을 찾아 내려가고, 의미가 다른 데이터를 잘못 연결하지 않습니다. AI가 탐색할 수 있는 경로를 세아의 업무 구조에 맞게 정의한 모습입니다.

그림 3. 세아 업무 온톨로지(가안). 각 상자는 MongoDB 컬렉션 하나에 대응하고, 화살표는 AI가 이동할 수 있는 분석 경로입니다.

온톨로지가 답하게 해 주는 질문

  • "이 오더는 어느 공장 · 어느 라인에서 생산되며, 그 라인의 자동화 설비 비율은?"
  • "이 설비는 어떤 기안으로 구매되었고, 지금 어느 법인에서 유휴 상태인가?"
  • "법인 간 내부 이관된 설비가 이관 후 실제로 가동되고 있는가?"
  • "BOM상 핵심 자재의 공장별 재고가 다음 달 오더를 감당하는가?"

먼저 고정해야 할 "공통 언어"

  • 조직 기준: 그룹 → 국가 → 법인 → 공장 → 부서의 공식 목록과 별칭
  • 보유의 정의: 사용중 · 유휴 · 불용 · 대여 · AS 중 무엇을 보유로 셀지
  • 분류 체계: 미싱(본봉 · 삼봉 · 오바 · 특종) · 자동화 · 기타의 확장
  • 금액 기준: 통화, 환율 기준일, 원가 열람 권한

06 · 질문 시나리오

경영진 질문 하나가 처리되는 과정

"이 지표가 왜 변했나?"라는 원인 분석 질문을 세아에 적용하면 다음과 같습니다. 숫자는 PoV 샘플 데이터의 참고용 집계이며, 원인은 데이터로 검증하기 전까지 가설로 표시됩니다.

질문: "그룹 전체 유휴 설비 중 어디에 몰려 있고, 왜 그런가?"

그림 4. 에이전트 분석 흐름. STEP 2~5의 순서는 고정이 아니며, 직전 결과에 따라 에이전트가 다음 도구를 고릅니다(가드레일 범위 안에서).

자동 생성되는 경영 브리핑 예시

Executive Snapshot
그룹 자산원장 기준 유휴 자산은 10,014건이며, 이 중 74%(7,453건)가 HTI 원장에 집중되어 있습니다. HTI 원장 내 유휴 비율은 53%로, 나머지 원장의 유휴 비율(0~9%)과 큰 차이를 보입니다.DB 집계 · 샘플 참고치
Key Drivers
HTI 원장의 유휴 자산은 여러 부서에 분산되어 있고, 일부 자산의 비고에 "유휴자산 등록(워싱동 보관)"처럼 보관 위치 이동이 기록되어 있습니다.원본 근거 있음
같은 기간 HTI 법인의 내부(법인 간) 매각 기록이 다수 확인되어, 설비 재배치 과정의 일시 보관일 가능성이 있습니다.주의 · 가설
Opportunity / Risk Signals
유휴 설비의 상태 전환 날짜가 원장에 없어 "언제부터 유휴였는지"를 판단할 수 없습니다. 상태 이력 관리 시 재배치 · 매각 의사결정의 근거가 강화됩니다.관찰 신호
→ 다음 확인: HTI 유휴 설비 중 다른 법인 수요와 매칭 가능한 미싱 · 자동화 설비 목록

PoV 샘플 데이터의 참고용 집계를 사용한 예시 문안으로, 전체 데이터 확보 후 수치가 달라질 수 있습니다. 원인 서술은 실제 운영 데이터와 현업 확인을 거쳐 확정해야 합니다.

현재 방식

  • AI가 파싱한 결과를 그대로 화면에 사용
  • 질문마다 AI가 데이터를 읽고 계산
  • 화면별로 집계 기준이 다름
  • 답변의 근거와 실행 과정이 남지 않음

권장 방식

  • AI 파싱은 유지하되, 원본 위치 기록 + 검증 규칙 통과분만 반영
  • 계산은 데이터베이스, AI는 해석과 문장 작성
  • 지표 정의를 한 곳에서 관리하고 모든 화면이 공유
  • 질문 · 조회 · 근거 · 답변을 저장해 재현과 감사 가능
성공의 기준은 "화면이 그럴듯한가"가 아니라 "같은 질문에 언제나 같은 숫자와 같은 근거가 나오는가"입니다. 1단계에서 질문 정답셋을 만들고 매 변경마다 자동으로 검증하는 것을 권합니다.
Appendix A

MongoDB로 가속하는 세아의 AX 여정

AX의 속도는 데이터를 얼마나 빨리 모으고, 믿을 수 있게 연결하고, AI에 안전하게 내어줄 수 있는지에 달려 있습니다. 여정의 단계마다 MongoDB가 줄여 주는 부분은 다음과 같습니다.

모으기제각각인 데이터를 있는 그대로

엑셀 행, PDF 기안서, 계층 구조의 BOM, 공장마다 다른 원장 양식을 억지로 표로 바꾸지 않고 문서 형태로 저장합니다. 새 양식이 생겨도 재설계 부담이 작습니다.

연결하기저장 · 검색 · 벡터 검색을 한 곳에서

업무 데이터 저장, 집계, 전문 검색, AI용 벡터 검색을 하나의 플랫폼에서 처리합니다. 별도 검색엔진 · 벡터DB를 붙이고 동기화하는 비용과 장애 지점이 줄어듭니다.

다듬기유연하되 품질 기준은 분명하게

필드 추가는 쉽게 하되, 스키마 검증 규칙으로 필수 항목 · 값의 형식을 강제해 "아무 데이터나 들어가는" 문제를 막습니다.

넓히기글로벌 공장으로 확장

MongoDB Atlas는 AWS · Azure · Google Cloud의 여러 리전에서 운영할 수 있어, 데이터 위치 규정과 해외 공장의 접근 속도를 함께 고려할 수 있습니다. 기본 구성부터 복제본을 두어 장애에 대비합니다.

지키기민감 정보 보호

저장 · 전송 암호화, 접근 권한, 감사 로그를 제공하며, 구매가 · 원가처럼 민감한 필드는 암호화된 상태로 조회하는 기능(Queryable Encryption)도 선택할 수 있습니다.

집중하기운영은 플랫폼에, 사람은 AX에

완전관리형 서비스로 백업, 보안 패치, 용량 확장을 플랫폼이 처리합니다. 세아 내부 인력은 인프라 운영보다 데이터 정의와 AX 과제에 집중할 수 있습니다.

여정에서 기대하는 변화

영역달라지는 점
의사결정 속도자주 묻는 지표는 사전 집계로 즉시 확인하고, 원인 분석도 같은 플랫폼 안에서 이어서 수행
신뢰성모든 수치를 원본 행까지 추적하고, AI 답변의 근거와 실행 과정을 보관
비용 · 복잡도저장 · 검색 · 벡터 검색을 하나로 통합해 운영할 시스템과 동기화 작업 감소
확장성자산원장에서 시작해 견적 · 설계 · 재고 · 에너지 · 문서로 같은 구조를 단계적으로 확장

위 효과는 구조적 특성에 기반한 설명이며, 정량 효과는 PoV 단계의 실제 측정으로 확인해야 합니다.
