DreamUS FLO Follow-up

AI 전환을 위한 MongoDB 기반 데이터·검색·벡터 검색 검토

DreamUS FLO 미팅 후속으로, MongoDB 최신 버전 업그레이드와 Search, Vector Search, Atlas 전환 가능성, 임베딩 모델 검증 방향을 한눈에 볼 수 있도록 정리했습니다.

핵심 방향

별도 벡터 데이터베이스를 먼저 구축하기보다, 통제 가능한 MongoDB 샌드박스에서 내부 운영 데이터 기반 검색과 벡터 검색을 빠르게 배포하고 검증하는 접근을 제안드립니다.

Executive Summary

-DreamUS의 주요 데이터는 정형 데이터 중심이며, 회사 내부 데이터(ERP, 작업 개발물, 로그 등)가 초기 AI 활용 후보가 될 수 있습니다.
-음악 데이터는 저작권에 따른 AI의 적극적인 도입 어려움이 일반적인 concern으로 존재하므로, 초기 AI 검증은 내부 통제 가능한 데이터부터 시작하는 방향이 현실적입니다.
-AI 도입 관점에서는 별도 벡터 DB를 새로 구축하기보다 MongoDB 환경에 Search 및 Vector Search 구성을 추가해 빠르게 배포하고 테스트하는 접근이 적합합니다.
-AI 워크로드는 통제 가능한 샌드박스에서 시작해야 하며, ODL·ODS 계층과 벡터 검색, LLM 연계 구간을 MongoDB 중심으로 관리하는 구조를 검토할 수 있습니다.
-MongoDB 최신 버전 업그레이드는 Search, Vector Search, RAG 및 Agent 활용까지 포함해 비용 비교 기준을 다시 잡는 것이 필요합니다.
-온프레미스 EA와 Atlas 동기화 하이브리드도 가능하지만, 비용·보안·운영 복잡도를 고려하면 EA 중심 또는 Atlas 중심 중 하나를 선택하는 방향을 권장합니다.

AI 도입 검증 방식

처음부터 큰 시스템을 만들기보다, 제한된 샌드박스에서 검색 품질, 응답 품질, 보안 통제, 운영 가능성을 순차 검증하는 방식이 안전합니다.

MongoDB 중심 샌드박스 아키텍처

AI 시스템은 원본 데이터, 임베딩 데이터, 검색 결과, LLM 처리 구간이 분산될수록 데이터 이동, 보안 통제, 감사, 운영 복잡도가 증가합니다. MongoDB를 중심으로 ODL 및 ODS 성격의 데이터 계층을 구성하면, 운영 데이터와 Search, Vector Search, LLM 연계 구간을 하나의 관리 체계 안에서 검증할 수 있습니다.

EA와 Atlas 아키텍처 선택지

선택지적합한 경우검토 포인트
EA 8.x 중심망분리, 데이터 주권, 온프레미스 또는 프라이빗 클라우드 운영, 직접 통제가 중요한 경우Search 및 Vector Search 구성, 운영 인력, 업그레이드 영향도, 하드웨어·라이선스 비용 검토
Atlas 중심운영 자동화, 빠른 확장, Managed Service, Atlas 기반 데이터 서비스 활용이 중요한 경우운영 부담 감소, Search/Vector Search 통합, 보안·네트워크 요건, 비용 구조 재산정
EA + Atlas 하이브리드EA를 원본 운영 시스템으로 유지하고 Atlas에서 Search/Vector Search를 수행하려는 경우데이터 동기화, 네트워크 경로, 보안 통제, 운영 이중화, 장애 대응, 비용 복잡도 증가 가능성

권장 방향

현재 단계에서는 EA 8.x 기반으로 Search 및 Vector Search를 함께 운영하는 방향, 또는 Atlas 중심으로 전환해 데이터베이스와 검색·벡터 검색을 일원화하는 방향 중 하나를 선택하는 것이 단순하고 현실적입니다.

하이브리드 고려 사항

EA와 Atlas를 동기화해 Atlas에서 검색을 수행하는 구조도 가능하지만, 동기화와 보안, 운영 이중화, 비용 관리가 복잡해질 수 있으므로 명확한 이유가 있을 때만 검토하는 것이 좋습니다.

MongoDB 최신 버전 업그레이드

1기술 작업 자체는 환경이 표준적이고 사전 이슈가 없으면 일반적으로 1~3 영업일 수준으로 볼 수 있습니다.
2사전 점검, 스테이징 테스트, 변경 승인 절차를 포함하면 1~2주 정도로 계획하는 것이 현실적입니다.
3라이선스 갱신이나 상업 조건 검토까지 함께 진행하면 전체 일정은 2~6주 정도로 보는 것이 안전합니다.

임베딩 모델 검토

Voyage AI 검토 포인트

Voyage 3.x 및 3.5 계열은 공개 벤치마크와 MongoDB 자료 기준으로 상위권 모델군으로 참고할 수 있습니다. 다만 Voyage 4 계열은 동일한 공개 리더보드에 충분히 반영되지 않았을 수 있으므로, 최신 모델이라는 이유만으로 확정하기보다 DreamUS 데이터 기준으로 평가하는 것이 적절합니다.

평가 방식

회사 내부 데이터(ERP, 작업 개발물, 로그 등) 일부를 대상으로 대표 질문 세트를 만들고, 임베딩 모델별 검색 정확도와 latency, 비용을 비교하는 방식이 적합합니다.

임베딩 모델은 범용 리더보드 순위만으로 결정하기보다, DreamUS의 실제 한국어 업무 데이터와 권한 통제 조건에서 retrieval 품질을 검증하는 것이 중요합니다.

비용 비교 기준 재정의

Database

기존 데이터베이스 운영 비용, 업그레이드, 라이선스, 하드웨어 또는 클러스터 비용

Search

전문검색, 자동완성, 하이브리드 검색, 검색 인덱스 운영과 확장 비용

AI

Vector Search, RAG, Agent 기반 활용, 임베딩 생성과 검색 품질 검증 비용

Operation

운영 자동화, 보안 통제, 모니터링, 장애 대응, 운영 인력 부담

과거의 EA와 Atlas 비용 비교는 데이터베이스 운영 중심이었다면, 현재는 Search, Vector Search, AI 서비스 확장성, 운영 자동화, 보안 통제까지 포함해 다시 비교하는 것이 적절합니다.
